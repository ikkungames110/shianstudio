# 顔タイプ診断：特徴量と画像バリエーションの改訂設計 ver3

作成日：2026-09-06。現行改訂：3.1.0（唇の上限・下ろし前髪の修正）。対象は[要件定義_ver2.md](要件定義_ver2.md)の #3〜#8 と画像生成計画。
[設計書_ver2.md](設計書_ver2.md)のうち、本書と競合する特徴量・配分・髪型・生成・レビューの仕様を本書で置き換える。集計・画面遷移など、それ以外はver2を引き継ぐ。男女各40人の計画と男性10人の試作を経て、承認された3.1.0の条件で全80人を制作し、現行診断の画像・対応データへ反映した。[全画像一覧](顔画像一覧_ver3.html)と[生成記録](顔画像生成_ver3.md)を参照。診断ロジックの実装変更は含まない。

## 1. 見直した点

前回は8つの印象タイプを起点に各5人を小さく変化させたため、輪郭・目・鼻・口の組合せが相関していた。また数値差をプロンプトの3段階へまとめ、全員に同じ髪型と抽象的な美形指定を与えていた。今回は診断タイプから顔を作らず、部位の形状を組み合わせ、その結果の印象を計算する。

整った容姿は全員の前提。丸い輪郭、幅のある顎、薄め〜中間の唇、一重に近いまぶたなども、それぞれ魅力的に成立させる。鼻・眉は日常的な範囲に限定し、形態の低値・高値を容姿の優劣として扱わない。

## 2. Level 1の確定仕様（要件 #3・#4）

形態は男女共通の**26連続項目**。ver2の24項目を維持し、`upper_lip_share` と `cupid_bow_definition` を追加する。全項目の名前・観察定義・両端は [feature_schema_v3.json](../data/plans/feature_schema_v3.json) を正本とする。目の2軸の5段階表現、口元の2軸の3段階表現と輪郭・髪型は生成スクリプトに定義し、その他の軸にはスキーマの3段階表現を使う。実際に使う全文は各人の `prompt` に保存する。

| 部位 | キー |
| --- | --- |
| 目：6項目 | `eye_angle`, `eye_shape`, `eye_size`, `eye_spacing`, `upper_eyelid_crease`, `lower_eyelid_fullness` |
| 眉：4項目 | `eyebrow_angle`, `eyebrow_arch`, `eyebrow_thickness`, `eyebrow_eye_distance` |
| 輪郭・配置：9項目 | `face_length_width`, `midface_ratio`, `lower_face_ratio`, `jaw_width`, `jaw_angularity`, `chin_width`, `chin_roundness`, `cheekbone_prominence`, `cheek_fullness` |
| 鼻：3項目 | `nose_bridge_height`, `nose_width`, `nose_tip_roundness` |
| 口・唇：4項目 | `mouth_width`, `lip_fullness`, `upper_lip_share`, `cupid_bow_definition` |

値は0〜1の設計座標で、人口の百分位や生成画像の実測値ではない。目の形・目尻の生成値は `0.15 / 0.325 / 0.5 / 0.675 / 0.85`。口幅・唇の厚さは `0.15 / 0.325 / 0.5` に限定し、上限を0.5とする。鼻・眉・その他の独立軸は `0.2 / 0.5 / 0.8`。輪郭9項目は実在しうる組合せを8種類の座標として定義する。

### 2.1 見た目の差を出すアンカー

| 軸 | 採用する段階・制約 |
| --- | --- |
| 輪郭 | 丸型、短い卵型、卵型、面長卵型、ベース型、長方形、逆三角型、菱形。横幅・顎角・頬骨・顎先の組合せで区別する |
| `eye_shape` | 丸い / 丸アーモンド / アーモンド / 細アーモンド / 切れ長。面積や目尻傾斜と別に割り当てる |
| `eye_angle` | 垂れ / やや垂れ / 水平 / ややつり / つり。目頭から目尻へ約 −4 / −2 / 0 / +2 / +4 度を生成上の目安とする。実測角度の保証ではない |
| `mouth_width` | 短い / やや短い / 中間。口角間の横幅。横に大きい口は生成対象にしない。「唇の長さ」はこの軸で扱う |
| `lip_fullness` | 薄い / やや薄い / 中間。厚い唇・膨らませた口元は生成対象にしない。閉口時の赤唇部の厚みを口幅に対して評価。口幅と配分を独立させる |
| `upper_lip_share` | 下唇主体 / やや下唇主体 / 上下が近い。値0〜1が上唇の割合30〜48%に対応し、計画値0.2/0.5/0.8は33.6/39/44.4%。上下の合計厚とは別軸 |
| `cupid_bow_definition` | 上唇中央の山がなだらか / 中間 / 明瞭。輪郭だけを変え、口紅・オーバーリップで作らない |
| 鼻幅 | 細め / 中間 / やや広め。小鼻を極端に広げない |
| 鼻筋 | 穏やかな立体感 / 中間 / 通った鼻筋。照明を変えて鼻高を演出しない |
| 鼻先 | すっきり / 中間 / 丸み。尖り過ぎ・過度な上向き・極端な変形を使わない |
| 眉形 | 直線 / 緩い曲線 / 自然なアーチ |
| 眉の太さ | 自然な細め / 中間 / しっかり。剃り眉や過度に濃い眉にはしない |
| 眉の傾斜 | 平行 / 少し上昇 / 自然な上昇。眉山とは独立させる |

鼻の前後方向・横顔の曲率は正面写真から安定評価できないため、今回は鼻幅・鼻筋の見かけ・鼻先を採用する。左右の目は同じ段階を指定し、表情や頭の傾きで垂れ目を作らない。

### 2.2 髪型の追加

`appearance_features.hair_style` をカテゴリとして別管理する。髪型には大小の連続的な順序がないため、26形態値に混ぜて平均しない。

| 共通キー | 男性 | 女性 |
| --- | --- | --- |
| `center_part` | センターパート | 肩丈のセンターパート |
| `fringe_down` | 軽く束が分かれた、前髪を自然に下ろす普通の短髪 | 肩丈の髪に、自然に下ろした前髪 |
| `up_bang` | 短髪アップバング | 肩丈で前髪を上げた額出し |

全員黒髪。下ろし前髪は眉にかかり、毛先が眉下付近に届く長さとし、目は隠さない。丸いお椀型・重いぱっつん・オン眉にはしない。旧キー `mash` は解釈違いを防ぐため `fringe_down` に変更する。髪型内で長さや質感の差を小さくし、頬・顎輪郭を見せる。眉の一部が前髪に隠れることは許容し、見えない眉の特徴は未確認扱いにする。女性のサイドは耳にかける。髪型の選択傾向はカテゴリ別の提示数・選択数で別集計し、今回の印象・8タイプへ直接加点しない。髪型が顔の選択に影響するため、本実装で顔の傾向を確認する際は同髪型のペアを優先する。各カテゴリの選択率を因果的な髪型の好みとは断定しない。クイズカードは引き続き画像のみを表示する。

`appearance_features.face_outline` は9個の輪郭座標を説明する補助カテゴリで、別の形態加点には使わない。

| 輪郭8種類 | 各5人 |
| 目の形・目尻 | 各軸5段階を各8人 |

まず輪郭を配り、各軸の値を別々に並べ替える。初回配分では各列について均衡配分した候補400通りを作り、すでに決めた列との分割表の偏り（カイ二乗統計量の合計）が最小の候補を採用する。口元2軸は既存の人物配分を維持したまま大きい側を中間へ制限するため、3段階の人数は均等ではない。完全直交の実験計画ではないが、単なるタイプ別の微差より部位の組合せを散らせる。解剖的に連動する輪郭9項目にはこの独立化を適用しない。

## 4. Level 2・変換・Level 3（要件 #5〜#8）

印象10項目は `cute`, `cool`, `mature`, `youthful`, `soft`, `sharp`, `glamorous`, `approachable`, `mysterious`, `androgynous` を維持する。各値は独立した0〜1で、かわいさとクールさを対立軸にしない。

変換は `shape-impression-1` を維持する。正本JSONの `mapping` に全重みを外出しし、項は `[変換, 形態キー, 重み]`。`p(x)=x`, `n(x)=1-x`, `b(x)=1-2|x-0.5|`。各印象の重み合計は1。新しい唇2項目と髪型には今回、根拠のない印象重みを追加せず、生成・詳細嗜好用として保持する。既存24項目には従来の重みがそのまま作用する。

8タイプもver2の `classic_cute`, `clean_soft`, `mature_elegant`, `cool_beauty`, `mysterious`, `friendly`, `androgynous`, `glamorous` を維持する。JSONの `type_prototypes` を上記変換に通し、小数3桁で四捨五入した10次元ベクトルを代表点とする。ユーザー印象と各代表点の平均二乗距離で最短のタイプを採用。同距離なら定義順。代表点を40人の生成制約には使わない。

選択形態の平均と `b(x)` 用の補助平均を保持するver2集計を継承する。新2項目は詳細な口元の嗜好に表示できるが、生成値を実測値のように表示しない。互換 `tags` は既存の10キーを維持し、生成目標からver2のadapterで計算する。`adult` は `mature`、`idol=0.6*cute+0.4*glamorous`、`shortFace=1-midface_ratio`。小数2桁で四捨五入する。

## 5. 生成・採用の手順

1. 男女各40人の26形態値・髪型・プロンプトを先に確定する。
2. プロンプトの冒頭に、その人固有の輪郭・目・唇を置き、続けて鼻・眉・髪型を明示する。目の2軸は5段階を維持し、口元2軸は許容範囲内の3段階を指定する。
3. 27歳の架空の日本人、自然で整った容姿、正面・頭部水平・閉口無表情、灰色背景・服、同じ柔らかい正面照明、realistic editorial beauty photo、`no text, no watermark` を共通にする。
4. 内蔵imagegenで1レコードにつき1人1枚。構図は頭・肩・胸中央まで引き、正規化時に背景の引き延ばしが発生しない余白を確保する。
5. `scripts/normalize_face_asset.py --input <raw> --dest assets/<gender>/<id>.png`（試作時は `assets/previews/v3/<gender>/`） で1200×1600、顔中心へ統一する。顔検出・余白補完なし・ファイル対応を確認する。
6. 生成画像を目視し、輪郭・目・唇・鼻・眉・髪型の読み取りやすさを確認する。指定が反映されなかった項目はレビュー記録に残す。設計値を実測済み形態値に書き換えたことにはしない。

試作10人は見た目の幅を確認するために制作し、修正後の承認画像を全件セットに再利用した。本番80件は `review_status=visual_checked` とし、画像の目視確認と形態値の実測校正を区別する。`shape_calibrated=false` を保持し、採点用の実測校正が済んだ `validated` とは扱わない。数値は自然な特徴の方向を指示するもので、生成器の角度・比率の厳密な再現を保証しない。

## 6. 無作為10人の扱いとファイル配置

男性40人から重複なしで10人を一度だけ抽出する。OS乱数でseedを作り、ID昇順の母集団にPython `random.Random(seed).sample(..., 10)` を適用する。抽出seed・順序・初回男性計画のSHA-256を生成前に [抽出記録](../data/previews/male_v3_selection.json) へ保存する。抽出結果が輪郭や髪型で均等になるような引き直しはしない。3.1.0でも同じ10人を維持する。初回計画のハッシュは `plan_sha256`、修正後は `current_plan_sha256` に保存し、抽出後の修正と初回抽出を区別する。

| 保存先 | 内容 |
| --- | --- |
| `data/plans/feature_schema_v3.json` | 26項目定義、印象変換、8タイプの原型 |
| `data/plans/male_faces_v3.json`, `female_faces_v3.json` | 生成前に確定した各40人の設計資料。計画時点の `image=null`, `review_status=planned`, `planned_image` を保持。生成後の実在パス・状態は本番データに記録 |
| `data/previews/male_v3_selection.json` | 生成前の抽出記録 |
| `data/previews/male_faces_v3.js` | 試作10枚だけのブラウザglobal `MALE_FACE_PREVIEW_V3`。実在する `image` と対応する全特徴・最終prompt・生成履歴 |
| `assets/previews/v3/male/male_NNN.png` | 試作の正規化画像10枚 |
| `docs/男性画像試作_ver3.html` | 10枚を並べた確認用ページ。画像一覧はIDだけを添え、特徴詳細は別欄で確認 |
| `data/male_faces.js`, `data/female_faces.js` | 現行診断の40人ずつ。全80人の最終画像パス・特徴量・最終プロンプト・目視記録 |

全件制作後に `assets/male/` と `assets/female/` の画像を対応する本番データと一緒に置き換えた。承認済み試作10枚と抽出記録は履歴として保持する。生成前の計画資料と実在画像はバージョン・状態で区別し、計画パスを公開画像として扱わない。
